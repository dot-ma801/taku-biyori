# ADR 0008: セッションは必ずロビーに属する（`game_sessions.lobby_id` を NOT NULL にする）

## Status

Accepted

## Context

v0.2 までのモデルでは、卓（`game_sessions`）が単独で存在できた。
「直接卓立て」——日程がすでに決まっている集まりを、参加者募集を挟まずに登録する経路——を
`lobby_id = NULL` で表現していたためである。

この形は、卓が「募集の器」と「1回の開催」の2つの役割を兼ねていたことの帰結だった。
v2 で概念モデルを Lobby（企画・受付の器）と GameSession（1回の開催）に分けたとき、
`lobby_id` を nullable のまま残すかどうかを決める必要が生じた。

### 解決したい課題

- `lobby_id` が nullable だと、セッションが「ロビーに属する場合」と「単独の場合」の2形態を持つ
- ホスト・招待トークン・定員・公開フラグは本来ロビーの属性だが、単独のセッションにも必要になる
- 表示値の導出（未設定ならロビーを参照。design-v2 §5-5）が「ロビーが無いかもしれない」分岐を抱える

### 検討した選択肢

1. **`lobby_id` を NOT NULL にする。** 直接卓立てでも必ずロビーを作る
2. **`lobby_id` を nullable のまま残す。** 単独のセッションを許す
3. **単独セッション専用のテーブルを別に持つ**

### 各選択肢の評価

| 観点 | 案1: NOT NULL | 案2: nullable | 案3: 別テーブル |
|------|--------------|--------------|----------------|
| セッションの形態の数 | 1つ | 2つ | 2つ（型が違う） |
| ホスト・トークン・定員の置き場所 | ロビーのみ | セッションにも複製が必要 | 両方に必要 |
| 表示値の導出（§5-5） | 常にロビーを引ける | ロビーの有無で分岐 | 分岐 |
| クエリ・API のパス | `/api/lobbies/:id/game-sessions/...` に統一 | 2系統 | 2系統 |
| 直接卓立ての手数 | ロビー作成が1ステップ増える | 増えない | 増えない |

## Decision

**`game_sessions.lobby_id` を NOT NULL にする。直接卓立てでも必ずロビーを作る。**

- 概念設計が「受付を開かないロビーに、最初からセッションが1つある」と明言している。
  直接卓立ては**ロビーの不在ではなく、受付を開かないロビー**として表現する
- ロビー作成という余分な1ステップは UI 側で1ボタンに隠せる。実際、ロビー作成画面の
  「日程が決まっている」モードが、ロビー作成と開催作成を1操作にまとめている（design-v2 §5-3 / §7-1）
- API のパスもこれに揃え、セッションは常に `/api/lobbies/:lobbyId/game-sessions/...` の下に置く。
  画面 URL も同じ階層にした（design-v2 §7-1）

## Consequences

### 良い点

- セッションの形態が1つになり、「ロビーが無いセッション」の分岐がコードから消える
- ホスト・招待トークン・定員・公開フラグをロビーだけが持てばよくなり、v0.2 でセッション側に
  重複していたカラムが復活しない
- 表示値の導出（未設定ならロビーを参照）が、常にロビーを引ける前提で書ける

### 悪い点・受け入れるコスト

- ロビー0件の状態で「とりあえずセッションだけ作る」ことができない
- テストデータの作成でも必ずロビーから作る必要がある（フィクスチャの `insertLobby` が前提）
- 直接卓立ての経路では、ユーザーから見えない下書きロビーが1件生まれる

## 決めていないこと

- 開催が0件のまま放置された下書きロビーの掃除。実ユーザーが付いてから判断する
