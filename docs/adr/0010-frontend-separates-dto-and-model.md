# ADR 0010: フロントエンドは API の DTO と内部 model を分ける

## Status

Accepted

## Context

`@taku-biyori/shared` はフロントエンドとバックエンドの**通信契約**を置く場所である。
v0.2 のフロントエンドは、この契約型（`LobbyDetail` / `GameSession` など）を
composable と component からも直接 import し、画面の内部構造としてそのまま使っていた。

このため、次の問題が起きていた。

- 日時が ISO 文字列のまま画面まで届き、表示のたびに `new Date(...)` を書く羽目になる
- レスポンスに無い導出値（在籍中の参加者だけの配列など）を、使う側がその場で毎回作る
- API の形が変わると、契約と無関係なはずの component まで一斉に壊れる
- 「レスポンスの形」と「画面が必要とする形」がずれていても、ずれを吸収する場所が無い

### 解決したい課題

- 通信契約の変更が画面に直接伝播する
- 変換（文字列 → `Date`、`leftAt` による絞り込みなど）が散らばり、同じ導出が複数箇所に生まれる

### 検討した選択肢

1. **`src/api/` を DTO と model の境界にし、`src/models/` に FE 用の型と変換関数を置く**
2. **shared の型をそのまま使い続ける**
3. **shared 側に FE 向けの型を足す**

### 各選択肢の評価

| 観点 | 案1: api/ で変換 | 案2: そのまま | 案3: shared に FE 型 |
|------|-----------------|--------------|---------------------|
| API 変更の影響範囲 | `api/` と `models/` に閉じる | 画面全体に波及 | shared 経由で両方に波及 |
| 日時・導出値の扱い | 変換の場所が1つ | 使う側が各自 | shared が FE の都合を持つ |
| shared の役割 | 通信契約に純化 | 契約 + FE の内部構造 | 契約 + FE の内部構造 |
| 変換のコスト | 変換関数とそのテストが要る | 不要 | 不要 |

## Decision

**`src/api/*.ts` を DTO と model の境界にする。ここより内側（composable / component）は
`@taku-biyori/shared` のレスポンス型を見ない。**

- `src/models/` に FE の内部型（`LobbyDetailModel` など）と、DTO から変換する関数を置く
- `src/api/*.ts` の各関数は DTO を受け取り、model を返す
- model では日時を `Date` にする。ただし**日付のみの値（`scheduledAt` / `openUntil`）は文字列のまま持つ**。
  `Date` にするとタイムゾーンで日付がずれるため
- 導出値（`activeEntries` など）は変換時に組み立て、使う側で毎回作らない
- 表示用のフォールバック文言（「未設定」など）は UI の関心事なので model には入れない

### 対象外

- **enum・`*Input` 型・権限関数・ステータス導出関数は shared から直接 import してよい。**
  これらは通信契約ではなく、FE と BE が同じ規則で動くために共有している定義そのもの
- `Profile` / `auth` まわりは v2 で触らないため、現状のまま残している

## Consequences

### 良い点

- API の形が変わったとき、直す場所が `src/api/` と `src/models/` に閉じる
- 日時変換と導出が1箇所にまとまり、`src/models/*.test.ts` で固定できる
- shared が通信契約に純化し、FE の都合が混ざらない

### 悪い点・受け入れるコスト

- 型と変換関数が二重に見える（DTO と model で似た形が並ぶ）
- 新しいエンドポイントを足すたびに変換関数とそのテストが要る

## 決めていないこと

- `Profile` / `auth` を同じ規約に揃えるかどうか。v2 のスコープ外なので保留している
