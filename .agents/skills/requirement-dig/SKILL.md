# 要望を掘り下げる

曖昧な要望を、次の段階（`concept-design` / `adr-creator` / `to-issues`）へそのまま渡せる
**共通理解**に変える。このスキル自身は概念もコードも書かない。

> エージェント側に同名の組み込みスキル（Claude Code の `/dig` など）がある場合の誤発火を避けるため、
> 名前を `requirement-dig` にしてある。組み込み側でも掘り下げ自体はできるが、
> taku-biyori では次段の振り先までこのスキルが持つので、こちらを呼ぶ。

## 進め方

1. **出発点を聞く** — 誰が困っているか、いま何ができなくて困っているか、なぜ今やるのか
2. **曖昧な言葉を具体化する** — 「使いやすくしたい」「便利にしたい」のような形容詞は、
   「誰が」「何を」「どう変えたいのか」まで分解して言い直してもらう
3. **スコープの境界を確認する** — 今回やること／やらないことをはっきりさせる。
   「ついでにこれも」が出たら、別の要望として切り分ける
4. **次の段を判定する**

   | 状況 | 次へ |
   |---|---|
   | 概念が怪しい（フラグが増える・条件分岐が無理になる） | `concept-design` |
   | 概念は素直だが、元に戻しにくい判断がある | `adr-creator` |
   | どちらにも当たらず、すぐ Issue 化できるほど固まっている | `to-issues` |

5. **「ここまでの理解」を短く要約してユーザーに提示する。** ズレがないか確認が取れるまで、
   次の段には進まない

## 心構え

- 一度に質問しすぎない。1回のやり取りで聞くのは1〜2論点まで
- 選択式で聞ける論点は AskUserQuestion を使う（無ければ番号付きの選択肢を提示する）
- 「共通理解が取れた」とみなすのはユーザーの明示的な確認があったときだけ。
  沈黙や話題転換を同意と解釈しない
- 実装や画面の話が先に始まったら、いったん要望の言語化に引き戻す
