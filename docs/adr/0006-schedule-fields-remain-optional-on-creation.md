# ADR 0006: 卓作成時に開催日・候補日のどちらかを必須にしない

## Status

Proposed

## Context

taku-biyori のフォーム UI では、必須項目にアスタリスク（`*`）を表示する対応を進めている。
その調査の過程で、卓（game session）作成・更新 API（`packages/shared/src/game-session.ts` の
`CreateGameSessionInputSchema` / `UpdateGameSessionInputSchema`）を確認したところ、
API 上「本当に必須」なフィールドは `title` のみで、開催日（`scheduledAt`）・候補日
（`game_session_candidates`）を含む他の全フィールドが任意であることが分かった。

一見すると「開催日か候補日のどちらかは必須にすべきでは」という直感が働く。
実際、卓作成フォーム（`InputScheduleInfo.vue`）には、候補日に値を入れると開催日の入力を
破棄する片方向の排他 UI が既にあり、両者は「どちらか一方を選ぶもの」という前提で
UI が組まれている。

一方で、`docs/design-v1.md`（日程調整設計セクション、および 8 章の意思決定ログ）には、
このアプリが前提とする本来のフローが明記されている。

```
open（募集中）
  │  参加者が集まったらホストが候補日を登録
  ▼
scheduling（日程調整中）
```

> `game_session_candidates` への候補日登録は、ステータスに関係なくいつでも登録できる。

つまり「調整さん」的に、ホストはまず日程を決めずに卓を公開し、参加者が集まってから
候補日を登録して調整する、という使い方が正規のフローとして設計されている。
卓作成 API に候補日を渡す手段自体も現状存在せず（候補日は作成後に
`PUT /api/game-sessions/:id/availability-dates` で別途登録する設計）、開催日・候補日と
もに未設定のまま卓を作成するのは想定内の状態である。

### 解決したい課題

- フォームの `*` 表示を、実際のバリデーション仕様と矛盾しない形で実装したい
- 「開催日 or 候補日のどちらかが必須では」という直感と、design-v1.md が明記する
  「まず日程を決めずに公開し、後から調整する」フローとの整合性を取りたい
- 副次的に見つかった実課題（募集締め切りを過ぎても候補日が0件のまま `scheduling` に
  留まり、ホストが気づきにくい）にどう対応するかを決めたい

### 検討した選択肢

1. **卓作成時に「開催日 or 候補日（1件以上）」を必須にする相関バリデーションを追加する**
2. **常時（作成・更新・候補日の個別追加/削除すべて）で同様の相関バリデーションを追加する**
3. **相関バリデーションは追加せず、現状の任意仕様のまま `*` は `title` のみに付ける**

### 各選択肢の評価

| 観点 | 案1: 作成時のみ必須化 | 案2: 常時必須化 | 案3: 現状維持 |
|------|----------------------|-----------------|---------------|
| design-v1.md のフローとの整合性 | 矛盾する（候補日を作成 API に含める手段がなく、「後から調整」を阻害する） | 矛盾する（`scheduling` の初期状態が成立しなくなる） | 整合する |
| 実装コスト | 中（候補日を作成 API に含める設計変更が必要） | 大（作成・更新・候補日追加/削除の全ユースケースにガードが必要） | 小 |
| 既存の「候補日はいつでも登録可能」という意思決定との整合性 | 一部矛盾 | 明確に矛盾 | 矛盾しない |
| 「候補日0件のまま scheduling」問題の解決 | 作成時のみ解決（運用中に発生するケースは未解決） | 解決するが副作用が大きい | 解決しない（別の緩和策が必要） |

## Decision

**卓作成・更新のどちらにおいても、「開催日 or 候補日のどちらかを必須にする」という
相関バリデーションは追加しない。UI の `*` 表示は API 上の実際の必須項目である
`title` のみに付ける。**

### 1. 相関バリデーションを追加しない理由

開催日・候補日の相関を必須化すると、design-v1.md が定義する「まず公開し、参加者が
集まってから候補日を登録する」という正規のフローと衝突する。とくに卓作成の時点では
候補日を渡す API 自体が存在しないため、「作成時必須」にすると実質的に「開催日を作成時に
決め打ちする」ことを強制するのと同義になり、後から日程調整するという本来の使い方を
狭めてしまう。

### 2. 代わりに対応する実課題

「開催日も候補日も未設定のまま `scheduling` に留まり、ホストが気づきにくい」という
実際の課題には、相関バリデーションではなく以下の軽量な対応で緩和する。

- **過去日を選択させない**: `openUntil`・`scheduledAt`・候補日の `date` について、
  フロントエンド（`BaseDatePicker` の `disablePast` prop）とバックエンド
  （`CreateGameSessionInputSchema` / `CreateAvailabilityDateInputSchema` への
  `.superRefine()` / `.refine()`）の両方で、過去日の指定を防ぐ。誤って過去日の
  募集締め切りを設定してしまい、公開直後から候補日ゼロのまま `scheduling` になる
  事故を減らす。
  - 更新系エンドポイント（`PATCH /api/game-sessions/:id` の `scheduledAt`/`openUntil`、
    `PUT .../availability-dates` の一括置換）には適用しない。これらは既存の値を
    無条件に含めて再送信する実装のため、過去日禁止を適用すると確定済み・過去日に
    なった卓の無関係なフィールド編集まで壊れてしまうリスクがあるため。
- **発見性の改善**: 候補日0件・`scheduling` の卓の詳細画面で、ホストに候補日登録を
  促す案内文を表示する（`ScheduleDisplay.vue`）。また、候補日が既に登録されている
  卓を編集画面で開いたとき、「複数の候補日を選択する」トグルを自動的に ON にする
  （`InputScheduleInfo.vue`）。

```ts
// packages/shared/src/game-session.ts
export const CreateGameSessionInputSchema = z
  .object({
    title: z.string().min(1).max(100),
    // ...
    openUntil: z.iso.date().optional(),
    scheduledAt: z.iso.date().optional(),
  })
  .superRefine((input, ctx) => {
    const today = todayDateString();
    if (input.openUntil && input.openUntil < today) {
      ctx.addIssue({ code: 'custom', path: ['openUntil'], message: '募集締め切り日には今日以降の日付を指定してください' });
    }
    if (input.scheduledAt && input.scheduledAt < today) {
      ctx.addIssue({ code: 'custom', path: ['scheduledAt'], message: '開催日には今日以降の日付を指定してください' });
    }
  });
```

## Consequences

### Positive

- design-v1.md が定義する「後から日程調整する」フローを妨げない
- `*` 表示が実際の API 仕様と完全に一致し、UI とバックエンドの認識がずれない
- 過去日禁止バリデーションにより、「候補日0件のまま scheduling」に陥る主要な原因
  （過去日の締め切り設定）を未然に防げる
- 発見性改善により、既にこの状態に陥った卓でもホストが復旧しやすくなる

### Negative

- 「開催日も候補日も未設定のまま `scheduling` になり得る」という状態は仕様として残る
  （API レベルでは防げない）
  - → 過去日禁止 + 詳細画面の案内文で、実際に発生する頻度と気づきにくさを下げることで緩和する
- 更新系エンドポイント（`PATCH`・一括置換）には過去日バリデーションを適用しないため、
  運用中に `scheduledAt` を過去日に更新することは技術的には可能なまま
  - → 実運用上ホストがそのような操作をする動機がなく、現時点では許容する

### Risks

- 将来「日程調整中のまま何ヶ月も放置される卓」が問題として顕在化した場合、
  本 ADR の判断（相関バリデーションを設けない）を見直す必要が出る可能性がある
  - → その場合はリマインド通知やステータス自動遷移など、バリデーションとは別のアプローチを
    検討する（候補日を必須化する方向には戻らない前提で検討する）

## 決めていないこと

| 項目 | 決めない理由 | いつ決めるか |
|------|------------|------------|
| 募集締め切りを過ぎても候補日0件の卓に対するリマインド通知 | 通知基盤自体が未整備で、今回のスコープを超える | 通知機能を実装するタイミングで再検討 |
| 更新系エンドポイント（`PATCH`・一括置換）への過去日バリデーション適用 | 既存値を無条件に再送信する実装のため、対応するには送信ロジック自体の見直しが必要 | フロントの送信ロジックを差分送信に変更するタイミングで再検討 |
