# 設計を Issue に割る

`dig` / `concept-design` / 設計書で固まった判断を、**そのまま着手できる Issue 群**に落とす。

## 0. 前提を確認する

次が揃っているときだけ着手する。1つでも欠けていたら Issue を書かず、その段へ戻す。

| 前提 | 欠けていたら |
|---|---|
| 何を作るかが決まっている | `dig` へ |
| 概念と語彙が決まっている | `concept-design` へ |
| 元に戻しにくい判断が記録されている | `adr-creator` へ |

**設計書にない仕様を、Issue を書きながら決めない。** 曖昧なら書く手を止めてユーザーに聞く。

## 1. 書く前に調べる

1. **文脈を集める** — 会話・`docs/design/v0.3/design-concept-model.md` の該当 §・トラッキング Issue
2. **現状を読む** — 既にあるもの、命名、同種の実装パターン
3. **語彙を合わせる** — 利用者に見せる名詞は CLAUDE.md の日本語ラベルに従う（卓 / 参加 / 日程調整 / 着席）
4. **prefactoring の機会を探す** — 先に変更しやすくしてから変える。必要なら独立した Issue にする

## 2. テストの切り口を決め、人間に合意を取る（省略不可）

**実装直前ではなく、Issue を割る前に決める。** どこでテストを切るかが Issue の割り方そのものを決めるため、
ここを飛ばすと実装段階で割り直しになる。

- 既存の切り口を優先する（backend のリポジトリ層 実DBテスト、frontend の `features/` composable テスト）
- **1機能あたり切り口は1つに絞る。** 2つ以上要るように見えたら、縦切りが足りていない兆候
- 切り口を提示して合意を取ってから 3 へ進む

## 3. 縦切りで割る

**1枚の Issue は、型 → API → 画面 → テストを貫く。** 満たすべき3条件。

1. **貫いている** — どれか1層だけで完結していない
2. **単体で確認できる** — 完了時点で画面から触れる、または `curl` で叩ける
3. **まっさらなコンテキスト1つに収まる**

```
❌ 層で割る
   shared の型 → backend → frontend    下流が上流の完了を待ち、並列化できない

✅ 縦で割る
   「日程に回答できる」1枚（型・API・画面・テスト）
   「回答を締め切れる」1枚
```

過去に層で割った #114 / #115 では、ブランチ間マージ（`52e676d` / `5e77898`）が発生している。

## 4. 例外: expand–contract

影響範囲がコードベース全体に及ぶ改修に**限って**、横切りを3段階で許す。

| 段階 | やること | 依存 |
|---|---|---|
| expand | 新しい形を旧と並べて足す。**何も壊れない** | なし |
| migrate | 呼び出し側を影響範囲ごとに更新。複数 Issue に割ってよい | expand |
| contract | 旧い形を消す | migrate 全部 |

`packages/shared` の型を先に入れるのは expand にあたる。**この3段階以外の横切り Issue は作らない。**

## 5. Issue のテンプレート

```markdown
## 何を作るか

{利用者の振る舞いで書く。「ホストが候補日を締め切ると、参加者には結果だけが見える」}
{層ごとの手順（まず型を足して、次に API を…）では書かない}

## 受け入れ条件

- [ ] {チェックできる粒度で書く}
- [ ] {画面またはコマンドで確認できる形にする}

## テストの切り口

{2 で合意したもの。どのテストでこの Issue の完了を判定するか}

## 参照

- `docs/design/v0.3/design-concept-model.md` §{番号}
- {関連 ADR があれば}

## 触るディレクトリ

- `packages/{...}/src/{...}`

## 依存

- {先に完了が必要な Issue 番号。なければ「なし」}
```

**タイトルはコミットと同じプレフィックスを使う**（`[add]` / `[update]` / `[fix]` …）。

## 6. 順序と並列

- **依存が「なし」の Issue が今すぐ着手できるもの**。これらは互いに衝突しないので並列に回せる
- 「触るディレクトリ」が重なる Issue は、依存が無くても**同時に走らせない**
- worktree は `../taku-biyori-issue-<番号>`、ブランチは `claude/issue-<番号>-<要約>`

## 7. 承認で止まる（省略不可）

割り終えたら**一覧を提示して止まる。** `gh issue create` は承認後に実行する。

聞くこと。

- 粒度は適切か（粗すぎ / 細かすぎ）
- 依存関係は正しいか
- 統合すべき／分割すべき Issue はあるか

## 8. 発行する

```bash
gh issue create --title "..." --body-file <path>
```

トラッキング Issue があれば、発行した番号をチェックリストとして追記する。
