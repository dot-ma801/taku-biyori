# ADR 0009: リポジトリ層は実 DB に対してテストする

## Status

Accepted

## Context

`infrastructure/` のリポジトリは、以前 drizzle のメソッドチェーンを `vi.fn()` でモックし、
組み立てられた SQL 文字列を assert する形でテストしていた。

この形は「呼び出しの形」を固定するだけで、**クエリが実際に正しい行を返すかを何も検証していない**。
実際、v2 への移行でクエリの条件が変わった箇所（`left_at IS NULL` による在籍者の絞り込み、
「最新の poll」の `created_at DESC, id DESC` によるタイブレーク、公開ロビーの導出条件など）は、
どれもモックでは差が出ず、SQL の意味が壊れていても緑のままになる。

### 解決したい課題

- クエリの結果ではなく形を検証しているため、条件の間違い・JOIN の取りこぼしを検出できない
- drizzle のメソッドチェーンをモックするコードが長く、クエリを書き換えるたびに壊れる
- 排他ロック（`FOR UPDATE` / `FOR KEY SHARE`）の挙動はモックでは原理的に検証できない

### 検討した選択肢

1. **`TEST_DATABASE_URL` が指す実 DB に対して実行する。** 各ケースはトランザクションでロールバック
2. **モックを続ける**
3. **PGlite / SQLite などのインメモリ実装に差し替える**

### 各選択肢の評価

| 観点 | 案1: 実 DB | 案2: モック | 案3: インメモリ |
|------|-----------|-----------|----------------|
| クエリ結果の正しさ | 検証できる | 検証できない | 概ね検証できる |
| 排他ロック・トランザクション | 検証できる | 不可 | PostgreSQL と挙動が違う |
| スキーマ・マイグレーションとの整合 | 実マイグレーションを適用して確認 | なし | 方言差で乖離しうる |
| 実行速度 | 遅い（数秒） | 速い | 速い |
| CI の準備 | PostgreSQL サービスが要る | 不要 | 不要 |

## Decision

**リポジトリ層のテストは `TEST_DATABASE_URL` が指す実 PostgreSQL に対して実行する。**

- 各テストはトランザクションで包み、終了時にロールバックする（`test/helpers/test-database.ts` の `withRollback`）
- テスト DB の作成とマイグレーション適用は `pnpm --filter @taku-biyori/backend db:test:setup` に集約する
- 接続先は `TEST_DATABASE_URL` **のみ**で切り替える。ローカルと CI で同じコードが動く
- 開発用 DB とは別のデータベースを指すこと（ロールバックするとはいえ、接続先は分けておく）
- テストは `test/integration/` に置く。`test/unit/` は引き続き純粋なユースケースのテストに使う

## Consequences

### 良い点

- クエリが「実際に何を返すか」を検証できる。条件の取りこぼしがテストで落ちる
- 排他ロックの競合（design-v2 §5-2 のセッション作成）を実際に再現して確認できる
- drizzle のメソッドチェーンをモックする長いコードが消え、テストがクエリの意味だけを語るようになる
- マイグレーションを適用した DB で走るため、スキーマとコードの乖離もここで落ちる

### 悪い点・受け入れるコスト

- テストの実行に PostgreSQL が必要になる。CI にサービスコンテナが要る
- 実行時間が伸びる（ユニットテストだけを回したいときは `test:unit` を使う）
- **開発コンテナがアイドルすると PostgreSQL が落ちる。** `relation "auth.user" does not exist` や
  フックのタイムアウトで大量に落ちたときは、まず `pg_isready` を疑う

## 決めていないこと

- 並列実行。現状は同じデータベースを直列に使っている。遅くなったらスキーマ単位の分離を検討する
