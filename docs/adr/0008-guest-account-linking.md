# ADR 0008: ゲスト参加のアカウント紐づけはホスト承認方式で行う

## Status

Proposed

## Context

本プロジェクトでは、募集枠（lobby）・卓（game_session）ともに **ログイン不要のゲスト参加**を提供している
（design-v1 §「ゲスト参加は『完全匿名 + トークンリンクのみ』」）。ゲストは `user_id = null` として
`lobby_members` / `game_session_members` に記録され、ホストが配布するゲストリンク
（`?token=<guest_link_token>`）を通じて参加・日程回答を行う。

この設計の帰結として、**ゲストとして参加した記録を後から取得したアカウントに紐づける手段がない**。
ADR 0001「ゲスト参加の扱い」でもこの制約が明示され、「ゲスト参加とログインユーザーの紐づけ」は
「設計コストが高く優先度が低い」として先送りされていた。本 ADR はその先送り事項に決着をつける。

### 解決したい課題

- ゲストで参加した人が後からアカウントを作っても、その参加がホーム画面の「あなたの卓」に出ない
  （`role` の判定が `user_id` ベースであるため）
- ゲストのままではプレイメモ（design-v1.2）を書けない。卓の記録が本人の手元に残らない
- ゲスト行は本人が退出することもできず、取り消しはホストに依頼するしかない

### 制約となっている既存の仕組み

| 事実 | 参照 |
|---|---|
| `guest_link_token` は募集枠/卓ごとの**共有**トークンで、メンバー単位ではない | `lobby-schema.ts` `guest_link_token` |
| トークンを持っていれば**どのゲスト列でも編集できる**（調整さん方式・本人確認なし） | `update-guest-availability-date-response.ts` の実装コメント |
| 公開済みの募集枠/卓は**未認証でも詳細を取得でき**、全メンバーの `id` が返る | `get-lobby.ts` / `list-members.ts` の可視性判定 |
| Google ログインの `callbackURL` は `/auth/callback` 固定で、認証往復で `?token=` は失われる | `GoogleLoginButton.vue` |

一方で、**データモデル自体は紐づけに適した形になっている**。`user_id` は nullable であり、
日程回答（`lobby_answers`）もプレイメモ（`game_session_play_memos`）も `member.id` に紐づくため、
紐づけは `user_id` を埋める UPDATE のみで完結し、子データの移し替えが発生しない。
確定済みの卓についても `game_session_members.lobby_member_id` で募集枠メンバーと相互に辿れる。

### 検討した選択肢

1. **ホスト承認方式** — ゲスト本人が紐づけを申請し、ホストが承認して `user_id` を確定する
2. **メンバー単位の claim_token 方式** — ゲスト参加時に高エントロピーなトークンを発行し、
   それを提示した者に紐づけを許可する
3. **localStorage 方式** — ゲスト参加時にクライアントへ識別子を保存し、それを根拠に紐づける

### 各選択肢の評価

| 観点 | 1. ホスト承認 | 2. claim_token | 3. localStorage |
|------|------------|----------------|-----------------|
| 本人確認の強度 | ホストの人間的判断（仲間内では十分） | トークン所持で機械的に判定 | **なし**（保存できるのは公開情報の `memberId` のみ） |
| 端末変更・時間経過への耐性 | 影響なし | リンクを保存していれば可 | **弱い**（後述） |
| DB スキーマ変更 | 申請テーブル 1 つ | メンバーへの列追加 | 不要 |
| クライアント側の新規機構 | 不要 | 保存先の設計が必要 | 必要 |
| ホストの手間 | 承認操作が発生する | 不要 | 不要 |
| 乗っ取りリスク | 低（承認が必ず挟まる） | トークン漏洩時に成立する | **高**（`memberId` は公開情報のため誰でも主張できる） |

**選択肢 3 の耐性が低い理由**（一般論ではなく本アプリの利用状況に基づく）:

- Safari / iOS の ITP は、7日間そのサイトを first-party として訪問しないと
  script-writable storage（localStorage・IndexedDB・`document.cookie`）を削除する。
  紐づけたくなるのは**卓の開催後**＝日程回答から数週間後であり、まさにその時点で消えている
- ゲストリンクは LINE や Discord で配布されるため、初回はアプリ内 WebView、後日は Safari 本体、
  という経路になる。**同一端末でも localStorage は共有されない**
- 保存できるのは `memberId` だが、これは公開済み募集枠なら未認証で取得できる情報であり、
  認証情報として機能しない

## Decision

**ゲスト本人が紐づけを申請し、ホストが承認することで `user_id` を確定する。
localStorage への識別子保存とメンバー単位 claim_token は採用しない。**

### 1. 申請と承認の流れ

```
ゲスト参加（user_id = null）
        │
        ├─ ゲストリンクを踏む → アカウント作成 / ログイン
        │
        ├─ 卓詳細画面で自分のゲスト行を選んで【申請】
        │     requested_user_id = セッションのユーザーID
        │
        └─ ホストが申請一覧から【承認】
              lobby_members.user_id = requested_user_id
              （lobby_member_id で対になる game_session_members も同時更新）
```

紐づけ先の `user_id` は**申請者のセッションから取る**。ホストがユーザーを検索して指定する形にはしない。
ホストにユーザー検索手段がないうえ、他人のアカウントを任意に指定できる設計は危険なため。

### 2. 認可の所在

認可は**ホストの承認 100%** に置く。申請そのものは権限行使ではなく情報の提出として扱う。

### 3. 申請に `Guest-Token` を要求しない

既存でトークンを必須にしているのはゲストの**書き込み** 2 操作
（`POST .../guest-members`・`PUT .../guest-responses`）のみで、閲覧系は要求していない。
申請もトークン不要とする。理由は次の 3 点。

1. **認証の往復でトークンが失われる。** `callbackURL` が固定のため OAuth を経ると `?token=` は戻らない。
   紐づけ申請は「リンクを踏む → ログイン → 申請」の順が必然なので、必須にすると必ずここで詰まる。
   回避するには token を往復中に保存するか `callbackURL` に載せることになり、
   design-v1 が明示的に避けた「認可キーをクエリ・保存領域に置く」形へ逆戻りする
2. **認可が強くならない。** トークンは募集枠ごとの共有秘密であり「本人である」ことを証明しない
3. **隠せる情報がない。** 申請に必要な `memberId` とメンバー一覧は公開済みなら未認証で取得できる

代わりに次の条件で絞り込む。

- 認証必須（`requested_user_id` はセッション由来）
- 対象が同一募集枠/卓の**ゲスト行**（`user_id IS NULL`）であること
- 対象が**公開済み**（`is_published = true`）であること。draft には申請させない
- `unique(member_id, requested_user_id)` により同一ユーザーの重複申請を防ぐ

### 4. 適用範囲は募集枠と卓の両方

片方だけでは、確定済みの卓が匿名メンバーのまま残る。承認時は
`game_session_members.lobby_member_id` を辿り、**対になる行を同一トランザクションで更新**する。

### 5. ステータスによる制限を設けない

既存のゲスト操作は `open` / `scheduling` に限定されているが、紐づけは
**完了済みの卓を履歴として取り込むことが主目的**であるため、ステータスで制限しない。

### 6. 重複メンバーはマージせず 409 で弾く

`(lobby_id, user_id)` の partial unique 制約があるため、申請者が既に同じ募集枠へ
ログイン参加している場合、承認は一意制約に衝突する。この場合は行をマージせず `409` を返す。
マージすると `lobby_answers` の `(candidate_id, member_id)` unique により
「どちらの回答を残すか」の判断が必要になり、暗黙のデータ選択が発生するため。

## Consequences

### Positive

- 新しい秘密情報を発行せず、クライアント側の永続化機構も追加せずに紐づけを実現できる
- 紐づけ後は既存ロジックがそのまま機能する。`role` 判定・プレイメモ・自己退出はいずれも
  `findMemberByUserId` 経由のため、専用の分岐を追加する必要がない
- 日程回答・プレイメモが `member.id` に紐づくため、紐づけによってデータが失われない
- 承認に人間の判断が挟まるため、仲間内で回す利用形態と実際の信頼関係が一致する

### Negative

- ホストに承認という手間が発生する
  - → 申請一覧を募集枠/卓の詳細画面に出し、1 クリックで承認できるようにする
- ホストが承認しない限り紐づかない。ホストが不在・多忙な場合は滞留する
  - → 将来的に claim_token 方式を追加すれば、ホストを介さない経路を用意できる（下記「決めていないこと」）
- 申請テーブルが 2 つ（募集枠・卓）増える
  - → 構造は同一で、既存の機能別スキーマ方針（ADR 0005）に収まる

### Risks

- 公開済みであれば誰でも申請できるため、無関係の第三者による申請スパムが理論上可能
  - → `unique(member_id, requested_user_id)` で同一ユーザーの重複を防ぎ、承認前の申請は
    ホストが却下できるようにする。実害は承認されない限り発生しない
- ホストが人違いで承認すると、他人の参加記録が別アカウントに紐づく
  - → 承認 UI に申請者のアカウント名を明示する。誤承認時はホストが当該メンバーを削除できる

## 決めていないこと

| 項目 | 決めない理由 | いつ決めるか |
|------|------------|------------|
| メンバー単位 claim_token による自動紐づけ | ホスト承認で機能要件は満たせる。トークン漏洩時の乗っ取り対策が別途必要になる | ホストの承認負荷が実際に問題として観測されたとき |
| 紐づけ済みメンバーの `guest_name` の扱い | `memberDisplayName` が `userName ?? guestName` の順で解決するため、残しても表示上の実害がない | 履歴表示に関する要件が出たとき |
| 重複メンバーのマージ | どちらの日程回答を残すかを機械的に決められない | マージ要求が実際に発生したとき |
