# 要求ドキュメント: 募集(卓立て前の日程調整枠)と卓の分離

> **作成日**: 2026-07-07
> **種別**: 要求定義(設計は本ドキュメントを元に別途行うこと)

---

## 1. 背景・解決したい問題

### 現状の問題

現在の RollHub では「卓(game_sessions)」が募集・日程調整・実施のすべてを1つのエンティティで担っている。このため、実際の利用フローが次のようになってしまう。

> 3人卓をやりたい → 空の卓を作成 → 5人に参加してもらう → 日程調整 → 3人の予定が合う日を見つけて、残り2人をキックする

これは体験として不自然であり、「メンバーをキックする」という強い操作をユーザー(ホスト)に強いる。また、このフローであれば調整さんで十分であり、RollHub を使う理由がなくなる。

### あるべき姿

マダミス/TRPG の実態は「多めに人を集めて、日程が合う人たちで開催する」である。これを自然に表現するには、次の2段階が必要。

1. **募集・日程調整のための枠**を作り、人を集めて日程を調整する
2. 調整の結果を元に、**同卓可能なメンバーを選んで卓を立てる**

「キック」は存在しない。選ばれなかった人は「今回の卓のメンバーにならなかった」だけで、募集枠の参加者であることは変わらない。

### この機能の位置づけ

「募集 → 選出 → 卓生成」の一気通貫フローは、既存グループの日程調整しかできない調整さんに対する RollHub の中核的な差別化ポイントである。

---

## 2. 新しい概念

| 概念 | 説明 |
|---|---|
| **募集枠**(仮称: recruitment) | 卓を立てる前の、参加者募集と日程調整のための枠。新概念 |
| **卓**(game_session) | 実際に開催されるセッション。日程とメンバーが確定した状態でのみ存在する |

募集枠から卓が生まれる。卓は募集枠を経由せずに直接作ることもできる(後述)。

---

## 3. 機能一覧

### 3-1. 募集枠の管理

- ホストは募集枠を作成できる(タイトル、シナリオ名、説明、定員、募集締め切り日)
- ホストは募集枠を公開/非公開にできる
- ホストは募集枠の内容を編集できる
- 募集枠の一覧・詳細を閲覧できる

### 3-2. 募集枠への参加

- ログインユーザーは公開中の募集枠に参加できる
- ゲストはゲストリンクから名前を入力して参加できる(既存のゲストリンクの仕組みを募集枠に対して適用する)
- ホスト自身も参加者として日程回答に加われる(既存方針を踏襲)

### 3-3. 日程調整

- ホストは募集枠に候補日を登録・削除できる
- 参加者は候補日に対して ◯△× で回答できる
- 回答の編集権限は既存方針を踏襲する(ログインユーザーは自分の回答のみ / ゲストは全ゲスト分編集可)

### 3-4. 卓の確定(本要求のコア機能)

- ホストは募集枠の日程調整結果を見て、**候補日を1つ選び、その日に参加できるメンバーを選出して、卓を作成できる**
- 選出対象は、確定候補日に ◯ または △ を回答したメンバーとする
- 選出対象が定員以内(または定員未設定)の場合は、全員をそのまま卓のメンバーにできる(手動選出の手間を発生させない)
- 選出対象が定員を超える場合のみ、ホストが手動で選出する
- 卓が確定したら、募集枠は「確定済み」となり、以降の日程回答・参加は受け付けない

### 3-5. 直接卓立て

- 募集枠を経由せず、日程・メンバーが最初から決まっている卓を直接作成できる(既存グループ向けの最短導線)
- 募集経由の卓と直接作成の卓は、作成後の扱い(実施・完了の管理)に差を設けない

### 3-6. 卓の管理(既存機能の位置づけ変更)

- 卓は「実施前 → 当日 → 完了」のライフサイクルのみを持つ(募集・日程調整の状態を持たない)
- 完了は引き続きホストの明示的なアクションで記録する(自動完了しない。キャンセル・延期を表現できるようにするため)

---

## 4. 非機能・UX上の要求

- **非選出者への表現**: 選ばれなかった人への表示・通知に「キック」「削除」「落選」といった強い言葉を使わない。「今回はご縁がなかった」系の柔らかい文言とする(toC向けの温かいトーンというプロダクト原則に沿う)
- **ステータスの導出方針の維持**: ステータスをDBに保存せず、ファクトデータから計算して導出する既存方針を新概念にも適用する
- **命名**: `session` が Better Auth と衝突する既存の事情は引き続き考慮すること。新概念(募集枠)の英語名は設計時に決定してよい(recruitment は仮称)

---

## 5. 実装上の制約・前提

- **初回本番デプロイは中止済み**。本番データは存在しないため、データ移行は考慮不要
- **既存実装(募集〜日程調整〜確定まで一通り実装済み)を壊さず、追加機能として段階的に実装する**こと。既存コードのロジック(候補日CRUD、◯△×回答、日程確定など)は新概念側へ流用・移植してよい
- 最終的に、旧来の「卓に直接ぶら下がる候補日・回答」の仕組みは廃止する。廃止のタイミングは新経路の動作確認完了後とする
- 各段階は独立した PR として提出すること

---

## 6. スコープ外

- 非選出者への通知機能(将来のリマインド通知機能と合わせて検討)
- 募集枠の検索・発見機能の強化(既存の優先度キューに従う)
- キャラクター管理・シナリオ管理との連携(Ph2)

---

## 7. 受け入れ基準(ざっくり)

- [ ] 募集枠を作成 → 公開 → 5人参加 → 日程調整 → 3人を選出して卓作成、という一連のフローが「キック」操作なしで完了できる
- [ ] 選出対象が定員以内の場合、手動選出のステップが表示されない
- [ ] 確定後の卓に、選出されたメンバーだけが表示される
- [ ] 募集枠を経由しない直接卓立てが引き続き可能
- [ ] 既存のゲストリンク参加が募集枠に対して機能する
