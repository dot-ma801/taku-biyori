taku-biyori バックエンドの API 仕様。

ロビー（企画）とセッション（開催）

ロビー（lobby）は企画であり、開催を重ねても解散するまで生き続ける。 セッション（game_session）は1回1回の開催で、必ずロビーに属する。 ロビーは参加者（LobbyEntry）を集め、日程調整（SchedulePoll）を何度でもやり直せる。 ホストが「その日に来られる人」を選んで着席（Seat）させると、1つのセッションになる。

v1.1 にあった「確定」という概念は消えている。募集枠が確定して卓へ転生するのではなく、 ロビーの配下にセッションが 0..n 件ぶら下がる。リスケは「中止 → 新しい日程調整 → 新しいセッション」で表す。

詳細は docs/design-v2.md を参照。

ステータス

ステータスはDB に持たず、ファクトカラムから導出する。導出関数は packages/shared に置き、 バックエンドとフロントエンドが同じ関数を呼ぶ（design-v2 §4-5）。

  • ロビー: draft（下書き）/ open（受付中）/ closed（受付終了）/ disbanded（解散）
  • セッション: scheduled（開催予定）/ today（本日開催）/ completed（完了）/ cancelled（中止）

認証

Better Auth（メール/パスワード・ソーシャルログイン）を利用。認証済みセッションの Cookie を リクエストに含めること。未認証の場合は 401 Unauthorized を返す。 ゲストは Guest-Token ヘッダーで参加・日程回答ができる。トークンはロビーに1つだけで、 セッション側にはトークンが存在しない。

エラーコードの使い分け

コード 判定するもの
400 ボディ・パラメータの構文と型（JSON パース失敗・zod の検証落ち）
401 セッション Cookie の有無
403 ロール・本人性・ゲストトークンの一致
404 リソースの存在と親子関係
409 ステータス以外の事実との衝突（重複・件数・最新性・並行実行）
422 ロール × ステータス（design-v2 §4-3 のポリシーテーブルが false）

判定は 400 → 401 → 403 → 404 → 409/422 の順に行う。 423 Locked は使わない（v0.2 の仕様書には記載があったが実装は一度も返していなかった）。

命名規則

  • URL は /lobbies・/game-sessions を使用
  • コード内の変数・型名は gameSession / GameSession プレフィックスを使用（Better Auth の session と衝突回避のため）
  • shared の型名には Lobby プレフィックスを付ける（barrel export の名前衝突回避）
  • DB カラム名は snake_case、JSON のキーは camelCase

ロビー削除

ホストのみ操作可能。次の3条件をすべて満たすときだけ削除できる。

  1. ステータスが draft
  2. ホスト以外の LobbyEntry が0件（**leftAt の有無を問わない**。脱退済みでも「他人が居た痕跡」として扱う）
  3. セッションが0件（v2 で追加。中止・完了のセッションも数に入れる）

3 を足したのは game_sessions.lobby_id が ON DELETE CASCADE になったため。 ロビーを消すと過去の開催記録・着席・プレイメモまで連鎖して消える。

ロビーのステータス遷移（公開・受付開閉・解散）

ロビーのファクトカラムを更新し、ステータスはサーバーが再導出して返す。ホストのみ操作可能。 target は v2 で open/cancelled の2値から open/closed/disbanded の3値になった。

target 書き込むファクト 許可する現ステータス
open is_published = true。open_until が今日より前なら NULL にクリアして受付を開き直す draft / open / closed
closed open_until = 昨日（サーバーのローカル日付 − 1日）。is_published は変えない open / closed
disbanded disbanded_at = now() draft / open / closed

open ⇄ closed は何度でも往復できる（追加募集）。disbanded は終端状態で、 そこからの遷移はすべて 422。同じ状態への遷移は冪等に成功させる。

未決: スキーマに「受付を閉じた」というファクト列が無いため、closed は open_until を昨日に書き換えることでしか表現できない。ホストが元々入れていた 締め切り日が失われる。lobbies.closed_at を足す案とあわせてレビューで決める （design-v2 §6-13-2）。

scheduled_at の作成・seats のバルク INSERT を1トランザクションで実行する。 ロビー行を SELECT ... FOR UPDATE した中で処理する（design-v2 §5-2）。

v0.2 との差分:

v0.2（confirm） v2
candidateId を受け取り候補日の date をコピー scheduledAt を直接受け取る
title・シナリオ・場所を卓へコピー コピーしない。上書きしたいときだけ任意入力
guest_link_token を新規生成 しない（トークンはロビーに1本）
closed_at をセットしてロビーを閉じる しない。ロビーは開いたまま
二重確定を条件付き UPDATE で排除 不要。同じロビーに複数セッションがあってよい

「候補日を選ぶ」のは UI の仕事で、フロントが選ばれた候補日の date を scheduledAt として送る。 GameSession → CandidateDate の出自リンクは持たない。

定員・回答内容（◯△×・未回答）によるサーバー側ブロックはしない（定員は目安、選出はホストが決める）。

セッションのステータス遷移（完了・中止）

セッションのファクトカラムを更新し、ステータスはサーバーが再導出して返す。ホストのみ操作可能。 target は v2 で open/completed/cancelled の3値から completed/cancelled の2値になった。

target 書き込むファクト 許可する現ステータス
completed completed_at = now() scheduled / today
cancelled cancelled_at = now() scheduled / today
  • open は受け付けない。セッションに公開の概念が無くなったため（公開はロビーの関心事）。
  • completed の条件が v0.2 の「today のみ」から scheduled も可に広がった。 開催日を過ぎたのに完了操作を忘れていたケースを救うため。
  • 逆方向（完了・中止の取り消し）は無い。どちらも終端状態。
  • v0.2 は cancelled への遷移だけポリシーテーブルを通さずハードコード判定していたが、 v2 では両方ともポリシーテーブル経由で判定する（design-v2 §4-5）。

中止した開催は削除せず「中止」として残る。リスケは「中止 → 新しい日程調整 → 新しいセッション」 で表す（design-v2 §5-1）。

着席させる（選出。ホストのみ）

ホストが指定した LobbyEntry を着席させる。**entryId 必須。ホスト以外は 403。**

着席は選出のファクトであり、選出はホストの仕事である。ログインユーザーもゲストも、 自分の操作は「ロビーに参加する」までで、着席させるのはホスト（design-v2 §6-6）。

v0.2 の「自分で着席する」経路と、ゲストの「参加 + 着席」（guest-seats）は どちらも廃止した。後者を持たない理由は2つ。

  1. ゲストだけが自分で Seat を作れると、「選出＝ホストが Seat を作ること」という v2 の中心的な主張が崩れる
  2. 招待リンクは /lobbies/{lobbyId}?token=… でロビーしか指していないため、 開催が2つあるロビーでは着席先が決まらない。成立するのは開催が ちょうど1つのときだけで、モデルはそれを保証しない

ホストによる代理の新規参加登録は持たない（entryId は既存の LobbyEntry でなければならない）。
